# Identity & Preferences Specification

> Purpose: This document specifies who a user is to the system, how a session becomes a `user_id`,
> and how the preferences that govern unit display, day boundaries, and goals are stored and applied.
> Every other feature spec assumes the conventions established here. See `specs/ARCHITECTURE.md` for
> the data conventions this spec instantiates.

## Overview

The product is single-user today and multi-user-ready by construction. That distinction is precise:
there is no signup funnel, no team, no sharing, and no billing — but every table carries `user_id`,
every query is scoped, and row-level security is enabled from the first migration. The cost is one
policy per table; the alternative is rewriting every query at the moment the stakes become real.

Identity has two halves. **Authentication** is delegated entirely to Supabase Auth — this system
stores no password, issues no token, and implements no reset flow. **Identity** is a `users` row
keyed by the auth subject, plus a `user_preferences` row that answers three questions the rest of the
system asks constantly: what units to display, where the user's day boundary falls, and what they are
aiming at.

Preferences are display-and-boundary concerns, never storage concerns. Switching from kilograms to
pounds changes what is rendered and what is parsed; it changes nothing in the database.

## Terminology

| Term | User-Facing | DB/Code | Definition |
| --- | --- | --- | --- |
| **Account** | Account | `auth.users` (Supabase) | Credentials and session, owned by Supabase |
| **User** | You | `public.users` row | The application-side identity, keyed by auth subject |
| **Preferences** | Settings | `user_preferences` row | Unit system, timezone, week start, energy unit |
| **Goal** | Goal | `user_goals` row | A target the user is working toward, with an effective period |
| **Session user** | — | `session.userId` | The `users.id` resolved from the request's auth cookie |

## Conceptual Layers

```
Supabase Auth          Application identity        Consumers
-------------          --------------------        ---------
auth.users      ──▶    public.users          ──▶   every user-owned table (user_id FK)
session cookie  ──▶    session.userId        ──▶   service layer, RLS context
                       user_preferences      ──▶   unit rendering, local_date, week boundaries
                       user_goals            ──▶   dashboard targets, agent context
```

`public.users.id` is generated by this system, not copied from the auth provider. The provider's
subject is stored alongside it as `auth_subject`. This keeps every foreign key in the schema pointing
at a UUIDv7 the application controls, and makes changing auth providers a single-column migration
rather than a rewrite of every reference.

## Data Model

### `public.users`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | UUIDv7, application-generated |
| `auth_subject` | `text` UNIQUE NOT NULL | Supabase `auth.users.id` |
| `email` | `citext` NOT NULL | Mirrored from the provider on each sign-in |
| `display_name` | `varchar(120)` NULL | Free text, shown in the UI only |
| `created_at` | `timestamptz` | `now()` |
| `updated_at` | `timestamptz` | `now()`, trigger-maintained |
| `deleted_at` | `timestamptz` NULL | Soft delete; blocks sign-in |

Indexes: `idx_users_auth_subject` (unique), `idx_users_email`.

### `public.user_preferences`

One row per user, created in the same transaction as the user.

| Column | Type | Notes |
| --- | --- | --- |
| `user_id` | `uuid` PK FK → `users(id)` `ON DELETE CASCADE` | One-to-one |
| `timezone` | `text` NOT NULL | IANA name, e.g. `Europe/Prague`. Default `UTC` |
| `mass_unit` | `mass_unit_enum` NOT NULL | `kg` \| `lb`. Default `kg` |
| `distance_unit` | `distance_unit_enum` NOT NULL | `km` \| `mi`. Default `km` |
| `energy_unit` | `energy_unit_enum` NOT NULL | `kcal` \| `kj`. Default `kcal` |
| `body_mass_unit` | `mass_unit_enum` NOT NULL | Separate from load: lifting in kg while weighing in lb is common |
| `week_starts_on` | `smallint` NOT NULL | ISO day 1–7. Default 1 (Monday) |
| `locale` | `text` NOT NULL | BCP-47, for number and date formatting. Default `en-GB` |
| `agent_config` | `jsonb` NOT NULL DEFAULT `'{}'` | The user's agent configuration; see below |
| `created_at` / `updated_at` | `timestamptz` | |

#### `agent_config`

The agent's per-user configuration, held as JSON rather than as columns because its shape is expected
to change more often than a migration cadence comfortably allows:

```json
{
  "skills": ["<skill uuid>", "..."],
  "effort": "high",
  "tone": null
}
```

`skills` is the enablement array consumed by `specs/skills/FEATURE_SPEC.md` § Flow 4. It carries no
foreign key — the cost of keeping enablement inside the configuration blob — so every consumer
tolerates IDs that are deleted or absent, resolving them defensively rather than failing.

### `public.user_goals`

Goals are periodized, not overwritten — a cut in March and a bulk in June are two rows, and a chart
of bodyweight against the goal in force at the time needs both.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` PK | |
| `user_id` | `uuid` NOT NULL | |
| `kind` | `goal_kind_enum` NOT NULL | `cut` \| `bulk` \| `maintain` \| `recomp` \| `performance` |
| `effective_from` | `date` NOT NULL | |
| `effective_to` | `date` NULL | `NULL` = currently in force |
| `target_body_mass_kg` | `numeric(6,3)` NULL | |
| `target_rate_kg_per_week` | `numeric(4,3)` NULL | Negative for a cut |
| `note` | `text` NULL | |
| `created_at` / `updated_at` / `deleted_at` | `timestamptz` | |

Indexes: `idx_user_goals_user_effective` on `(user_id, effective_from DESC)`.

Nutrition targets live in `nutrition_targets` (see `specs/nutrition/FEATURE_SPEC.md`) rather than
here. A goal is an intent; a target is a number the day view checks against, and the two change on
different cadences.

### Enums owned by this spec

`mass_unit_enum`, `distance_unit_enum`, `energy_unit_enum`, `goal_kind_enum`. The cross-cutting
`source_enum` is defined in `specs/ARCHITECTURE.md` and used by every feature spec.

## Session Contract

Every server entry point resolves a session before touching the service layer:

```
request → Supabase session cookie → auth_subject → users row → { userId, preferences }
```

Resolution is memoized per request. Three outcomes:

| Condition | Result |
| --- | --- |
| No valid session | Redirect to sign-in (UI) or 401 (API) |
| Valid session, no `users` row | Provision on the spot (see Flow 1), then proceed |
| Valid session, `users.deleted_at` set | 401, session invalidated |

The resolved `userId` is passed explicitly into service functions. It is never read from a request
body, never accepted as a tool argument, and never inferred from anything the client controls.

### RLS context

Every database connection sets the session user before executing a statement, so RLS policies
evaluate against it:

```sql
SET LOCAL app.user_id = '<uuid>';
```

Policies take the shape `USING (user_id = current_setting('app.user_id')::uuid)`. Catalog tables add
`OR user_id IS NULL` for read, and forbid write where `user_id IS NULL`.

This is defence in depth, not the primary control. The service layer scopes every query on its own;
RLS exists so that a missed `WHERE` clause returns nothing rather than returning another user's data.

## User Roles & Permissions

There are no roles. A user reads and writes their own rows, reads system catalog rows, and cannot
address another user's rows at all.

| Action | Own rows | System catalog rows | Another user's rows |
| --- | --- | --- | --- |
| Read | Yes | Yes | No (404) |
| Create | Yes | No (403) | No (404) |
| Update | Yes | No (403) | No (404) |
| Delete | Yes | No (403) | No (404) |

## User Flows

### Flow 1: First sign-in and provisioning

1. The user authenticates through Supabase Auth.
2. Session resolution finds no `public.users` row for the `auth_subject`.
3. In one transaction: insert `users`, insert `user_preferences` with defaults, insert a
   `maintain` `user_goals` row effective today.
4. `timezone` is seeded from the `Intl.DateTimeFormat().resolvedOptions().timeZone` value the client
   submits on first load; `locale` from `navigator.language`. Both are hints, both are overridable,
   and neither is trusted for anything but presentation.
5. The user lands on onboarding.

Provisioning is idempotent on `auth_subject`. Two concurrent first requests resolve to one row via
the unique constraint, with the loser re-reading rather than erroring.

### Flow 2: Onboarding

A four-step form, each step skippable, writing through the same service functions as the settings
screen:

1. **Units** — mass, distance, energy, bodyweight. Defaults inferred from locale.
2. **Timezone and week start** — prefilled from the browser.
3. **Goal** — kind, target bodyweight, target rate.
4. **Nutrition targets** — handed to `specs/nutrition/FEATURE_SPEC.md`; either entered directly or
   computed from bodyweight, activity, and goal, with the computed values written as a normal
   editable target row rather than a derived value.

Onboarding is complete when step 1 is saved. Everything else can be filled in later, and the
dashboard degrades to what it has.

### Flow 3: Changing units

1. The user changes `mass_unit` from `kg` to `lb`.
2. `user_preferences` updates. **No other table is touched.**
3. Every rendered load converts at display time; every numeric input parses as pounds and converts to
   kilograms before it reaches the service layer.
4. Historical data is unaffected — a 100 kg squat renders as 220.5 lb, and the stored value stays
   100.000.

The conversion boundary is enforced by types: service functions accept branded `Kilograms`,
`Grams`, `Metres`, `Seconds`, and `Kilocalories` values. A raw `number` from a form does not satisfy
the signature, so a forgotten conversion is a compile error rather than a silent 2.2× error in the
data.

### Flow 4: Changing timezone

1. The user changes `timezone`.
2. `user_preferences` updates. Existing `local_date` values are **not** rewritten.
3. New rows compute `local_date` in the new zone.

Rewriting history would change what days past entries belong to, re-bucketing totals the user has
already seen and reasoned about. The stored `local_date` records the day as the user lived it; a
traveller's log correctly shows the day they were in at the time.

### Flow 5: Deleting the account

1. The user confirms deletion with a typed confirmation.
2. `users.deleted_at` is set; the session is invalidated; the Supabase auth user is deleted.
3. A durable job hard-deletes owned rows and storage prefixes (`imports/<userId>/`,
   `artifacts/<userId>/`, `skills/<userId>/`) within 30 days.

The soft-delete window exists to make an accidental deletion recoverable. After the job runs,
deletion is terminal, and the UI says so before the confirmation rather than after.

## API Surface

Preferences and goals are edited through Server Actions; there are no public routes. The session
contract above is consumed by every route handler listed in `specs/ARCHITECTURE.md` § API Surface.

| Action | Purpose | Failure modes |
| --- | --- | --- |
| `updatePreferences(patch)` | Partial update of `user_preferences` | 400 with field errors on an invalid IANA zone or out-of-range week start |
| `createGoal(input)` | New goal; closes the open-ended prior goal by setting its `effective_to` | 400 on overlapping periods |
| `updateGoal(id, patch)` | Edit a goal | 404 if not the caller's |
| `deleteAccount(confirmation)` | Flow 5 | 400 if the confirmation does not match |

## Invariants

1. Exactly one `user_preferences` row exists per non-deleted user, created in the same transaction as
   the user.
2. `user_id` used in any write is the session-resolved value. No code path accepts it as input.
3. At most one `user_goals` row per user has `effective_to IS NULL`.
4. `user_goals` periods for a user do not overlap.
5. Preference changes never modify rows in other tables.
6. `local_date` values, once written, are immutable under preference changes.
7. `timezone` is a valid IANA identifier, validated against the runtime's timezone database on write
   — not a regex, and not an offset.
8. Every user-owned table in every spec has an RLS policy keyed on `app.user_id`.
9. `agent_config.skills` is not referentially enforced; every consumer tolerates deleted or absent
   skill IDs.

## Key Design Decisions

**Application-owned user id, provider-owned auth.** Foreign keys point at a UUIDv7 this system
generates. The auth provider's subject is one indexed column. Changing providers, or adding a second,
touches that column and the session resolver — not the forty foreign keys that would otherwise
reference it.

**Preferences are presentation, not storage.** The unit conversion happens at exactly two points: the
form parser and the renderer. Any design where a preference change implies a data migration is a
design where the preference cannot be changed casually, which is the opposite of what a settings
toggle promises.

**Branded unit types.** A convention that says "always store kilograms" is enforced by code review
and therefore eventually violated. A `Kilograms` branded type moves the enforcement to the compiler,
where the cost of a mistake is a red squiggle rather than a year of subtly wrong training volume.

**Goals are periodized rows, not mutable fields.** A mutable `current_goal` column loses the history
that makes the chart meaningful: the point of plotting bodyweight is to see it against what was being
attempted at the time.

**Single user, full scoping.** RLS, `user_id` columns, and session-derived ownership are written now
at a cost of roughly one policy per table, against a retrofit cost that touches every query in the
system and arrives precisely when real data is at stake.

## Observability

- `auth_session_resolve_total{outcome=ok|provisioned|unauthenticated|deleted}`
- `user_provisioned_total` — expected to be 1 in normal operation; a second is worth a look
- `preferences_updated_total{field}`
- `account_deletion_total{stage=requested|purged}`

RLS policy violations are logged at `error` with the table and the attempted `user_id`. In a
correctly functioning system this counter never increments, which makes it a useful alarm.
